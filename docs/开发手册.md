## 📚 1. 核心架构透视

Scooprym Music 是一个典型的高并发、异步处理的 SaaS 应用。

### 1.1 技术栈深度选型
- **Next.js 15 (App Router)**: 利用 React Server Components减少客户端 Bundle 体积，提升首屏速度。
- **PostgreSQL + Drizzle ORM**: 相比 Prisma，Drizzle 提供了更接近 SQL 原生的控制力，且冷启动速度更快，非常适合 Serverless 环境。
- **Better Auth**: 抛弃 NextAuth.js 的复杂黑盒，选择 Better Auth 以获得更灵活的数据库 Session 控制 (Schema 位于 `src/db/schema.ts` 的 `session` 和 `account` 表)。
- **Tailwind CSS 4.0**: 采用最新的 CSS 引擎，零运行时开销。

### 1.2 目录结构精选
```text
src/
├── app/api/              # 核心业务接口 (非 Page 路由)
│   ├── generate/lyrics/  # [POST] 歌词生成入口
│   ├── generate/music/   # [POST] 音乐生成入口 (返回taskId)
│   ├── polling/music/    # [GET]  前端轮询生成状态

```

## 🚀 2. 核心业务全链路解析 (The Core Pipeline)

这是整个项目的灵魂。我们采用 **"同步响应 -> 异步处理 -> 状态轮询"** 的架构，以解决 AI 生成耗时过长（30s+）导致 HTTP 连接超时的问题。

### 2.1 阶段一：提交生成 (Submission)
1. **用户操作**: 在 `/create` 页面点击 "Generate"。
2. **API 调用**: `POST /api/generate/music`。
3. **后端处理**:
    - 校验用户积分余额（此时**不扣除**）。
    - 调用 `src/ai/music/lib/generation.ts` 向 MiniMaxi 发起异步请求。
    - **关键点**: MiniMaxi 不会立即返回音频，而是接受请求并排队。
    - 创建数据库记录 (`song` 表)，状态设为 `processing`。
    - 立即返回 `songId` 给前端。

### 2.2 阶段二：自动化工作流 (The Workflow)
文件位置: `src/lib/creation/song-workflow.ts` -> `processMusicBackground`

这是一个在后台运行的复杂状态机，并行执行以下任务：

#### 任务 A：音频管道 (Audio Pipeline)
1. **下载**: 从 MiniMaxi 回调或链接下载原始音频流。
2. **转储**: 将 Buffer 上传至兼容 S3 的 Cloudflare R2 (`src/storage/index.ts`)。
3. **更新 DB**: 将 `processingStatus` 更新为 `audio_uploaded`。

#### 任务 B：封面管道 (Visual Pipeline)
1. **生成**: 并行调用图像模型，生成 1:1 封面。
2. **上传**: 将图片 Buffer 上传至 S3。
3. **关联**: 更新 `song` 表的 `coverImageUrl`。

### 2.3 阶段三：结算与完成 (Finalization)
仅当**任务 A (音频)** 成功后，才会触发计费逻辑：
1. **扣除积分**: 调用 `src/credits/credits.ts`，记录 `credit_transaction`。
2. **状态终结**: 将 `processingStatus` 更新为 `completed` (或 `completed_without_cover`)。
3. **前端感知**: 前端轮询接口检测到 `completed`，展示播放器。

## 🏗️ 3. 前端复杂状态管理 (State Resilience)

为了防止用户在生成过程中手滑刷新页面导致任务丢失，我们实现了一套健壮的**恢复机制**。

### 3.1 Store 设计 (Zustand)
文件: `src/store/create-store.ts`

- **持久化**: 使用 `persist` 中间件，将 Store 状态存入 `localStorage`。
- **关键字段**:
  ```typescript
  interface CreateState {
    processingTaskId: string | null; // 正在进行的任务 ID
    lyrics: string;                  // 当前编辑的歌词
    musicPrompt: string;             // 选中的风格
    reset: () => void;               // 一键重置函数
  }
  ```

### 3.2 恢复逻辑 (Resume on Hydration)
1. 用户刷新页面。
2. `CreateMusicPage` 组件挂载 (Hydrate)。
3. 从 `localStorage` 读取 `processingTaskId`。
4. 如果 ID 存在，Hook `useMusicGeneration` 会立即将内部状态置为 `generating`，并重启对该 ID 的轮询。
5. 用户看到的界面会无缝回到 "Cooking..." 状态。

## 💰 4. 支付系统深度解密 (Stripe Integration)

我们不仅接入了 Stripe，还解决了一个经典的分布式系统难题：**Webhook 延迟与状态不一致**。

### 4.1 "系统分身" 难题
当用户在 Stripe 页面支付成功后，重定向回我们的 `/success` 页面时，Stripe 的 Webhook 可能还没到达我们的服务器。此时如果只依赖 Webhook，用户会看到 "未通过" 或 "积分未到账"。

### 4.2 解决方案：主动同步策略
核心函数: `syncStripeDataToKV(customerId)`

无论触发源是谁，我们都主动去 Stripe 拉取最新状态：
1. **场景 A (前端重定向)**: 用户到达 `/success` -> 前端请求后端 -> 后端调用 `syncStripeDataToKV` -> 强制更新 DB -> 用户看到到账。
2. **场景 B (Webhook)**: Stripe 异步通知 -> 后端接收 -> 调用 `syncStripeDataToKV` -> 确保数据最终一致性。

### 4.3 数据库模型 (`payment` 表)
- `invoiceId` 设置为唯一索引，防止重复扣款/发货。
- `status`: 严谨映射 Stripe 的 `active`, `past_due`, `canceled` 等状态。

## 🛠️ 5. 基础设施注意事项

### 5.1 存储 (Storage / S3mini)
- **局限**: 由于使用了轻量级的 `s3mini` 客户端，我们**不支持生成预签名 URL (Presigned URLs)**。
- **后果**: 所有文件上传必须经过我们的应用服务器透传 (`Upload -> App Server -> S3`)，而不能直接从浏览器直传 S3。
- **配置**: 必须在环境变量中设置 `STORAGE_ENDPOINT` (包含 Bucket 名)。

### 5.2 数据库迁移 (DB Migrations)
开发流程必须严格遵守：
1. 修改 `src/db/schema.ts`。
2. `pnpm db:generate` (生成 SQL 文件)。
3. `pnpm db:push` (应用到开发库)。
4. 严禁手动修改数据库结构，否则 Drizzle 会状态失步。

## ⚠️ 6. Windows 开发避坑指南

### 6.1 编码地狱 (Encoding Hell)
Windows PowerShell 默认使用 GBK (CP936) 处理重定向，这会导致 UTF-8 代码文件瞬间乱码。
- **禁止**: `echo "中文" > file.ts`
- **必须**: `Set-Content -Path file.ts -Value "中文" -Encoding UTF8`
- **检查**: 保持 VS Code 右下角永远显示 `UTF-8`。
