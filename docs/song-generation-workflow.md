# 歌曲生成工作流

## 目标

把“新闻 → 歌词 → 音频 → 封面 → 成品检查 → 发布”从一个长请求拆成可观察、可恢复、可审计的阶段。任何一次模型调用都必须属于唯一的 `workflowRunId`，昂贵结果一旦落库，不因后续阶段失败而重新生成。

管理员界面只展示六个业务阶段：`Source Preparation → Lyrics Studio → Music Production → Cover Production → Product Check → Publish Ready`。数据库继续保留更细的执行步骤，便于恢复与审计。

## 业务流程

```text
新闻素材
  ↓
歌词创作管线 ──失败──→ 记录失败，可重新发起一次歌词尝试
  ↓ 安全与质量门禁通过后自动提交；只有异常内容才进入 Lyrics Review
异常审核 ──批准──→ 保存修订并继续制作
        └─拒绝──→ 终止本次运行
  ↓
音频排队
  ↓
生成音频 ──失败──→ 仅失败当前运行，不生成封面
  ↓
上传音频 ──失败──→ 保留失败记录，可单独重试上传
  ↓ 持久化 audioUrl/audioKey 检查点
生成并上传封面 ──失败──→ 停在封面阶段，保留音频并只重试封面
  ↓
最终入库
  ↓
成品检查 ──失败──→ 修复对应资产或元数据，只重跑检查
  ↓
可发布 ──发布/排期──→ 已发布
```

## 阶段定义

| 阶段 | 含义 | 是否调用付费模型 | 恢复策略 |
| --- | --- | --- | --- |
| `source_ready` | 新闻素材已准备 | 否 | 可重新编辑 |
| `generating_lyrics` | 运行事实、艺术视角、双稿和编辑审校管线 | 是 | 新建步骤尝试 |
| `analyzing_source` | 与歌词规划合并完成素材清洗和新闻简报 | 是 | 不再产生一次独立模型等待 |
| `planning_lyrics` | 同一次调用生成简报、事实账本、艺术视角和策略候选 | 是 | 合法检查点可直接复用 |
| `drafting_lyrics` | 两个不同策略包的完整 A/B 稿已生成 | 是 | 编辑失败时不重写双稿 |
| `editing_lyrics` | 编辑选优与事实终审在同一次调用中完成 | 是 | 从本地确定性终检继续 |
| `verifying_lyrics` | 本地规则、预计时长与合并事实审计结果已执行 | 是 | 保存门禁结果 |
| `lyrics_review` | 安全或质量门禁要求管理员决定 | 否 | 可修改后批准，或拒绝本次运行 |
| `lyrics_ready` | 标题、最终歌词和 Writers' Room 结果已持久化 | 否 | 自动提交音频制作；可从此检查点恢复 |
| `queued_audio` | 制作请求已入队 | 否 | QStash 去重投递 |
| `generating_audio` | MiniMax 官方 Music 2.6 生成音频 | 是 | 同一任务使用 CAS 防止重复消费 |
| `uploading_audio` | 下载、校验并上传音频 | 否 | 失败不进入封面阶段 |
| `audio_uploaded` | 音频已形成持久化检查点 | 否 | Worker 可从这里直接续跑封面 |
| `generating_cover` | 生成并上传 1K 方形封面 | 是 | 失败保留音频，只重做封面；兜底图不能通过发布门禁 |
| `finalizing` | 原子更新歌曲与生成记录 | 否 | 使用已保存的音频继续收尾 |
| `checking_product` | 检查标题、歌词、永久音频、封面、来源和真实时长 | 否 | 修复后可单独重跑，不调用模型 |
| `publish_ready` | 客观交付条件通过 | 否 | 允许管理员试听后发布或排期 |
| `published` | 已由管理员发布 | 否 | 保存发布审计记录 |
| `completed` | 兼容旧运行的完成阶段 | 否 | 读取时折叠为 Publish Ready |
| `failed` | 当前尝试失败 | 否 | 错误和步骤历史保留 |

## 数据边界

- `song_creation_run`：一次端到端创作，保存当前阶段、人工审核状态、素材快照和最终歌词。
- `song_creation_step`：每个阶段的每次尝试，保存供应商、模型、开始/完成时间、结果摘要与错误。
- `generation_attempt`：音乐生产任务的幂等、队列和计费记录。
- `song`：仅保存可供产品消费的歌曲资产；音频上传完成后立即写入，作为恢复检查点。

`song_creation_run` 负责业务编排，`generation_attempt` 负责音乐任务执行，两者不互相替代。

## 歌词创作管线

歌词属于平台创作资产，MiniMax 只负责作曲、演唱与制作，不负责改写歌词。创作阶段固定、具体 Meme 表达形式动态选择，管线如下：

1. **来源分析与策略规划**：一次调用整理素材支持的事实、带出处的说法和禁止推断，选择讽刺对象、艺术视角、喜剧切入点、Hook 与叙事蓝图。提出三个策略候选后选定唯一策略，不生成 B 稿或 hybrid。
2. **单稿写作**：结合素材、音乐方向和制作方案生成一份完整歌词，目标 14–24 个演唱行、90–140 个英文词、45–65 秒。实际音频时长由音乐生成结果决定。
3. **一次定稿**：同一次调用完成事实、创作和格式审查并返回完整定稿。检查 Hook 的可理解性、自然重音、铺垫和落点，修复周围具体问题；保留已选锚句和策略，锚句本身的问题记录为创作建议，不自动更换 Hook 或追加审查轮次。

正常路径仍是三个主要模型调用：`来源分析与策略规划 → 单稿写作 → 一次定稿`。安全复核、失败重试或供应商切换可能增加调用。

### 策略检查

- 提示词和本地检查共享 `lyrics-meme-strategy.ts` 中的规则。
- 原句重复检查次数与开头位置；延迟揭晓和一次性包袱检查只出现一次且位于结尾。
- 变体重复、问答、递进列表、首尾呼应由现有定稿模型判断语义关系，不强制逐字重复或两个副歌标签。
- 无显式重复策略不统计锚句次数。代码只检查可确定的格式、长度及对应位置要求。
- 质量与事实审查的剩余问题只提供编辑建议，不增加人工批准步骤。素材不可用、安全最终判定不允许和基本歌词格式损坏仍中止流程。

### 局部重写

重写接口接受工作流 ID，由服务端按当前管理员身份加载素材及创作记录，传入事实账本、讽刺对象、视角、蓝图、锚句和策略规则。模型只修改选中片段，保持段落作用与上下文关系。普通重写不增加、移除或替换已选锚句，不新增 Hook 调整工作流。

前端核对请求前后的歌词、歌曲和工作流，防止旧响应覆盖期间的手工修改或另一首歌。手工修改、采用草稿及局部重写共用歌词状态入口，自动刷新本地建议并将旧模型审查标记为已过期；这不会阻断音乐生产或触发额外模型调用。旧编辑笔记保留但明确标注为历史笔记。

### 音乐交接

根据最终歌词和 Production Recipe 单独生成 MiniMax 制作指令；MiniMax 请求固定 `lyrics_optimizer: false`。歌词模型的可唱性判断不代表已经通过真实音频听评。

## API 契约

- `POST /api/generate/lyrics`：在调用模型前创建运行；成功返回 `workflowRunId`。
- `POST /api/generate/music`：接受 `workflowRunId`，将人工确认后的歌词绑定到歌曲并排队。
- `POST /api/generate/workflows/:runId/review`：管理员批准或拒绝处于 `lyrics_review` 的歌词；批准时可同时保存编辑后的标题和歌词。
- `POST /api/worker/generate-music`：仅接受 `songId`，所有可信参数从数据库读取。
- `GET /api/generate/workflows/:runId`：返回当前用户自己的运行与完整步骤历史。
- `POST /api/generate/workflows/:runId/retry`：只重试音乐生产或无模型的成品检查；每次尝试保留独立历史。
- `POST /api/generate/cover/retry`：只替换封面，沿用已经持久化的音频，随后自动重跑成品检查。
- `GET /api/songs/:id/processing-status`：同时返回客户端状态、六阶段 `phase`、细粒度 `currentStage` 与错误信息。

## 可靠性规则

1. 先持久化，再调用模型。
2. 每个阶段单独记录，不覆盖历史失败。
3. 音频与封面顺序执行但状态解耦；封面绝不能拖垮或重触发音频。
4. 音频上传成功立即落库，硬中断后从 `audio_uploaded` 续跑。
5. 旧歌曲没有 `workflowRunId` 时继续走兼容路径。
6. 前端只负责提交和展示，不能决定 Worker 的用户、计费或供应商参数。
7. 歌词规划、双稿、编辑和终检分别写入步骤日志；相同 `workflowRunId` 且输入指纹一致时复用合法检查点，避免末端失败后重复支付前面的模型调用。
8. `/api/generate/music` 必须验证工作流处于 `lyrics_ready`；`lyrics_review`、`failed` 或其他阶段一律拒绝进入音频队列。
9. 发布与排期必须经过 `checking_product`，且工作流进入 `publish_ready`；通用兜底封面、缺失存储键、HTML 换行残留和 30–90 秒以外的已知时长都会阻止发布。
10. 失败时 `currentStage` 必须保留真实失败位置；Queue 根据它提供定点 Retry，不把任务退回整条流水线。


## 歌词失败与等待预算（2026-09-10）

- 文本模型单次尝试默认 75 秒，同一阶段最多等待 180 秒、最多三个目标。歌词 HTTP 请求内各阶段共用 240 秒截止时间；接口执行窗口为 300 秒，为失败落库与响应保留余量。这是异常等待预算，不是正常生成耗时承诺。
- 连接被对端关闭和供应商通用错误可以降级；账户 401/402 不再在同一账户内重复切模型。模型名称、歌词长度与创作质量要求不变。
- 后台任务遇到输入 422、权限 403 等不可恢复错误，按 QStash 协议返回 489 和 `Upstash-NonRetryable-Error: true`，不再自动重复拒绝同一选题。供应商临时错误仍使用检查点恢复。
- 新检查点记录模型阶段的真实开始时间与耗时；歌词错误保留 planning/drafting/editing 的真实失败阶段，避免统一显示 generating_lyrics。
- 2026-09-10 只读排查确认：历史存在供应商错误、连接中断、定稿 360 秒超时、旧双策略规则失败与同一禁区选题反复重试。OpenRouter 凭据校验返回 200，OpenAI 备用凭据返回 401；未修改任何凭据，也未重新投递历史任务。
