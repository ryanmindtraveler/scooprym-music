# 本地热点队列

热点雷达使用数据库保存任务，再由 QStash 签名投递各个歌词检查点及音乐任务。云端 QStash 无法回调 localhost；本地开发必须启动官方开发服务器或使用受控公网隧道。

## Windows 本地配置

1. 将 `@upstash/qstash-cli` 安装到 F 盘运行目录，例如 `npm install --prefix F:/CodexHome/runtimes/qstash @upstash/qstash-cli@2.37.18`。
2. 首次运行该包 `bin/qstash.exe dev`，把其输出的 `QSTASH_URL`、`QSTASH_TOKEN` 和两项签名密钥填写到不提交 Git 的 `.env.development.local`。
3. 同一文件配置 `QSTASH_LOCAL_BINARY` 为可执行文件绝对路径。
4. 使用 `pnpm dev`。启动器会验证现有本地队列或启动队列，然后启动 Next.js；由启动器创建的队列在开发服务器结束时一并关闭。

不要把本地测试凭据部署到线上，也不要把生产密钥交给本地测试队列。生产环境仍要求可公开访问的 Worker 和完整签名校验。

## 验证与限制

- `POST /api/admin/story-radar/:id/generate` 只持久化和投递，不导入歌词/音乐执行模块。
- 相同新闻使用固定任务、运行及歌曲 ID，重复点击不重新创建歌曲。
- 投递失败必须显示失败，不能仅凭数据库行存在就伪装成已经排队。
- 本地 QStash 为官方内存开发服务，重启后消息会丢失。数据库中的任务和检查点不会丢失；重新点击对应新闻可以投递 queued 任务并复用已有检查点。
- 本地队列不是生产部署方案；后台持续执行要求开发服务器和本地队列保持运行。
